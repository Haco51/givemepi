# PR-0029: Measurement and Bottleneck Optimization

## 전제

PR-0028의 Concurrent I/O, data movement 기본 구현, LZ4 backend가 먼저
commit/push되어야 한다. PR-0029는 구현된 storage pipeline의 실제 병목을
재현 가능한 방법으로 측정하고, 측정 결과가 있는 부분만 최적화한다.

## 반드시 유지할 계약

- PR-0028의 chunk identity와 canonical codec bytes 유지
- NodeLifecycle durability 및 Progress telemetry 호환성 유지
- synchronous fallback 유지
- sync/async P/Q/T 결과 동일성 유지
- memory budget과 bounded queue 상한 유지

## 구현·검증 순서

### 1. 측정 환경과 acceptance 기준 고정

- Release build, compiler, CMake 설정, CPU, filesystem, kernel, commit 기록
- 100 MiB/512 MiB/1 GiB와 single/multi-chunk workload 정의
- sync/async, worker 1/2/4/8, queue 1/4/16/64 조합 정의
- cold-cache와 warm-cache 분리
- warm-up 1회 후 최소 5회 반복
- median/min/max/p95, throughput, peak RSS, queue/backpressure,
  spill/reload, 실패 수, P/Q/T 결과를 기록

### 2. 단계별 telemetry 완성

- file read/write
- CRC32C
- compression/decompression
- GMP encode/decode
- header/checksum/index publication
- queue wait와 worker별 active time

현재 working tree에는 단일 chunk의 `StorageTiming`과 일부 단계 계측이
추가되어 있다. PR-0028 변경과 분리한 뒤 PR-0029 기준에 맞게 확장한다.

### 3. 전체 workload matrix 실행

- 100/512 MiB 및 가능한 1 GiB single chunk
- multi-chunk spill/reload
- sync와 async 비교
- worker/queue 조합별 처리량과 backpressure 비교
- none/LZ4 압축률·CPU·store/reload throughput 비교
- raw sample과 summary를 함께 보존

### 4. 병목 원인 분석

- CRC32C: buffer 접근과 SIMD 경로 확인
- file I/O: read/write, fsync, rename, directory sync 분리
- GMP: allocation, serialization, payload copy 확인
- queue: capacity 부족, worker imbalance, index publication 대기 확인
- peak RSS: 원본 P/Q/T·encoded·decoded buffer lifetime 확인

### 5. 최적화 구현

1. bounded buffer 재사용과 buffer lifetime 단축
2. encode/decode streaming 검토
3. CRC32C와 file read 경로 최적화
4. GMP serialization/decode allocation 및 copy 최적화
5. queue backpressure와 worker scheduling 조정
6. mmap/prefetch/io_uring/preallocation/batch index commit은 측정상 이득이
   확인될 때만 선택

각 최적화 후 동일 workload, checksum, P/Q/T, restart/integrity 테스트를
반복한다.

### 6. 대형 데이터 안정성 검증

- Release 512 MiB round-trip 재검증
- 1 GiB workload의 memory budget과 peak RSS 확인
- ASan/UBSan storage/codec 및 저메모리 대형 workload 실행
- partial file, restart, CRC corruption, cleanup 검증
- sync/async P/Q/T와 lifecycle 결과 비교

현재 확인 상태:

- Release 512 MiB none/LZ4 round-trip: 통과
- ASan/UBSan storage·codec 테스트 및 32 MiB LZ4: 통과
- 1 GiB와 100 MiB 이상 sanitizer workload: 전용 메모리 조건에서 재검증 필요

### 7. 플랫폼 최적화 판단

- NUMA placement, Huge Pages, worker affinity를 workload별로 비교
- 현재 runner는 1 NUMA node이고 explicit Huge Pages가 없어 기본 적용하지 않음
- 다른 장비에서 이득이 입증된 경우에만 opt-in 설정으로 추가

### 8. 최종 정리

- 5회 반복 및 p95 결과를 baseline/optimized 표로 정리
- 개선율과 메모리 비용을 함께 기록
- 회귀가 있으면 최적화 제외 또는 feature flag 처리
- PR-0029 acceptance gate 확인
- 문서화 후 PR-0029 commit/push

## PR-0029 완료 조건

- 재현 가능한 workload matrix와 raw sample 보존
- 단계별 병목과 수정 효과 수치화
- 대형 Release 및 sanitizer 검증 완료 또는 명시적 장비 제한 기록
- 기존 correctness/lifecycle/progress 계약 회귀 없음
- 최적화가 실제 workload에서 개선을 증명함
